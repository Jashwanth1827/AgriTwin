# Public deployment: Render or Railway

AgriTwin is a **three-part app**:

1. **Frontend** — the React website (built into nginx).
2. **Backend** — FastAPI, the trained crop-health model and the decision engine.
3. **Database** — PostgreSQL, plus a small disk for uploaded leaf photos and Grad-CAM overlays.

The crop-health artifacts are about **1 GB**, so use a paid **Starter**-size web service. The free tier does not have enough memory.

> Never put a real `DATA_GOV_API_KEY` in `render.yaml`, `railway.json`, Discord, chat or GitHub. Set it only in the provider dashboard.

---

## Option A — Render (recommended, easiest)

The repository includes `render.yaml`, which describes the database and both web services.

1. Sign in to <https://dashboard.render.com>.
2. Click **New → Blueprint**.
3. Connect GitHub and select `Jashwanth1827/AgriTwin`, branch `main`.
4. Keep the service names:
   - `agritwin-backend`
   - `agritwin-frontend`
5. When asked for `DATA_GOV_API_KEY`, either paste a key you own or leave it unset. Without a key the app uses the keyless five-state mirror.
6. `JWT_SECRET_KEY` is generated automatically. Do not replace it with your data.gov.in key.
7. Click **Apply**. The first build takes a while because PyTorch is large.
8. Open the frontend URL shown by Render, usually:

   ```text
   https://agritwin-frontend.onrender.com
   ```

9. Demo login:

   ```text
   demo@agritwin.in
   Demo@12345
   ```

10. Verify the API:

   ```text
   https://agritwin-backend.onrender.com/api/v1/system/health
   ```

Expected response:

```json
{"status":"ok","app":"AgriTwin","version":"1.0.0","environment":"production","demo_mode":true,"database":"ok"}
```

### Render details already handled for you

| Item | Setting |
|---|---|
| Database | Render PostgreSQL, connected with the Psycopg 3 driver |
| Uploads / Grad-CAM | 1 GB disk mounted at `/app/uploads` |
| Backend URL for nginx | `BACKEND_ORIGIN=https://agritwin-backend.onrender.com` |
| CORS | Frontend and backend Render URLs |
| Login secret | Generated by Render, never stored in Git |

If you rename a service, update `CORS_ORIGINS` on the backend and `BACKEND_ORIGIN` on the frontend to the new URLs. `BACKEND_ORIGIN` must not end with `/`.

## Option B — Railway

Each service has its own small config file (`backend/railway.json` and `frontend/railway.json`). Railway reads the file from the service root directory.

1. Sign in to <https://railway.app> and create a **New Project**.
2. Choose **Deploy from GitHub repo** and select `Jashwanth1827/AgriTwin`.
3. Add a **PostgreSQL** plugin to the project.
4. Create the **backend** service:
   - Root directory: `backend`
   - It will use `backend/Dockerfile`.
   - Add a persistent **Volume** mounted at `/app/uploads`.
5. Set these backend variables in the Railway dashboard:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Copy from the PostgreSQL plugin (`postgres://...` is accepted) |
   | `JWT_SECRET_KEY` | Generate a long random string; do not use your data.gov.in key |
   | `ENVIRONMENT` | `production` |
   | `DEMO_MODE` | `true` for the project demo |
   | `UPLOAD_DIR` | `/app/uploads` |
   | `CORS_ORIGINS` | `https://<your-frontend-domain>` |
   | `LIVE_MARKET_PROVIDER` | `auto` |
   | `DATA_GOV_API_KEY` | Optional; leave empty for the keyless mirror |

6. Create the **frontend** service:
   - Root directory: `frontend`
   - It will use `frontend/Dockerfile`.
   - Set `BACKEND_ORIGIN` to the backend public domain, for example
     `https://agritwin-backend.up.railway.app` with **no trailing slash**.
7. Generate public domains for both services.
8. Open the frontend domain and log in with the demo credentials above.
9. Check:

   ```text
   https://<your-backend-domain>/api/v1/system/health
   ```

## Local Docker still works

Nothing about the deployment changes local development:

```powershell
docker compose up -d --build
```

Then open <http://localhost:5173>. The frontend nginx container uses
`BACKEND_ORIGIN=http://backend:8000` by default.

## Before making it a real public system

For a college demo, `DEMO_MODE=true` is fine. For real users:

1. Set `DEMO_MODE=false`.
2. Create real accounts through `POST /api/v1/auth/register`.
3. Replace the demo password.
4. Keep `JWT_SECRET_KEY` secret and unique.
5. Keep the database password secret and unique.
6. Add your own `DATA_GOV_API_KEY` only in the provider dashboard if you want nationwide official mandi rates.

If deployment fails, read the provider logs, but **do not paste log lines containing `api-key`** into chat or issues.
